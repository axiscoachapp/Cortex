# Cortex workflow and functionality reassessment

Review date: 2026-10-28 (America/Sao_Paulo). Baseline: local remediation branch at `1ad2116`.

This is a source review and synthetic execution review, not a production clinical evaluation. No real patient data, model calls, Google calendar mutations, or application implementation changes were used. The first-launch context supplied during the review is Haddad Nicola in Curitiba, with gynecology/obstetrics and urology as the relevant specialties. The user clarified that all doctors will launch with separate patient lists and optional patient sharing. Reception is outside the initial scope. PersonalMed2005 export files already exist, but their migration is a later task; this review did not inspect them.

## Assessment

The app has a useful consultation-documentation workflow: patient context, recordings, drafts, physician review, chart history, document generation, and a calendar. The previous security and data-durability work materially improves that foundation. It remains a predominantly **individual clinician workspace** rather than a product with explicit clinician-to-clinician sharing. The clinic launch needs reliable encounter identity, clear patient demographics, reviewable clinical provenance, and private-by-default records with explicit sharing grants. Membership in the clinic must not automatically expose every doctor's patients.

Four isolated probes execute the real UI components or the transpiled production handler with synthetic dependencies. A passing probe means the reported defect was reproduced; it does **not** mean the issue is fixed. Run them with:

```powershell
npx vitest run --config docs/reviews/2026-10-28/workflow-probes.config.mts
```

Results are recorded in `workflow-probe-results.json`. These files use `.probe.ts`/`.probe.tsx` and a separate config, so they are excluded from normal `.test` discovery. Backend probes replace PostgREST, authentication, quota, Storage, and model network boundaries; they do not establish real provider or database integration behavior.

## Confirmed findings and focused risks

| ID | Priority | Finding | Evidence and trigger | Remedy and acceptance |
|---|---|---|---|---|
| W1 | P1 | Unknown optional age becomes age zero | `src/components/NewConsultationModal.tsx:49,65` explicitly accepts an empty age then submits `0`; `src/pages/Index.tsx:233` persists it. `src/components/ChatPanel.tsx:332` and `supabase/functions/chat-assistant/index.ts:139` use that value as clinical context. The actual component probe submits a blank optional age and records `age:0`. | Preserve unknown as nullable/explicitly unknown, or require an explicit age until the model supports unknown. Never infer a newborn. Prefer date of birth plus encounter-date age, with source/verification status. Tests must distinguish unknown, actual age zero, birthdays, and imported records. |
| W2 | P1 | Finishing one encounter completes every appointment for that patient today | `supabase/functions/finalize-consultation/index.ts:246–256` updates all scheduled/confirmed rows for the same patient and clinic day, without an appointment identifier. The handler probe finishes a morning visit and observes an unrelated later appointment also become `realizado`; next-day and canceled controls remain unchanged. | Carry an optional owned `appointment_id` through encounter/draft/finalization. Complete only the linked appointment; an unscheduled encounter must not complete any appointment. Cover two same-day visits, retry, canceled appointment, and cross-owner linkage. |
| W3 | P1 | New AI-generated longitudinal history bypasses physician review | `supabase/functions/finalize-consultation/index.ts:296–349` makes a second model extraction after the physician-approved SOAP is saved, then writes empty `medical_history`/`social_anamnesis` automatically. The probe returns synthetic facts absent from the approved SOAP and observes them persist. CAS prevents competing updates but does not provide clinical approval. | Return versioned pending suggestions with source excerpts; persist only the exact clinician-accepted text. Include history in the review step or a separate acceptance card. Test that model-only facts remain pending, rejection leaves the chart unchanged, and approval binds the source/revision. This is a verified review-gate gap; the probe does not claim a measured real-model hallucination rate. |
| W4 | P1 | Assistant can present a limited retrieval window as the complete chart | `supabase/functions/chat-assistant/index.ts:105,112` fetches only five visits and eight files; note/document excerpts are then truncated. At line25 the system prompt explicitly instructs “não foi anexado” when an exam is absent from the supplied document block. An existing ninth-most-recent exam cannot appear in that block. | Make retrieval question-aware and return source IDs, dates, excerpt boundaries, and coverage limitations. Distinguish “not found in the retrieved context” from “not present in the chart.” Test a requested older exam and an older visit, a missing result, and unavailable retrieval. Confirmed context construction/prompt defect; a live model’s exact wording was not tested. |
| W5 | P2 | Certificate duration can be silently changed during issuance | `src/components/DocumentComposerModal.tsx:183–196,293,411` accepts any positive number; generation is an `onClick` outside form validity enforcement. Actual component probe enters366 while the input reports range overflow and still calls generation with366. `supabase/functions/generate-prescription/index.ts:144` clamps it to365; a positive value below0.5 similarly becomes0.5. | Reject invalid/nonfinite/out-of-range durations consistently in UI and API, preserving the requested value for correction. Never normalize a clinician’s requested duration into a different issued duration without confirmation. Cover lower/upper bounds, step rules if intended, fractions and nonnumeric API input. This is software data integrity, not a recommendation about a clinically appropriate duration. |
| W6 | P2 | Scheduling a new patient fabricates a last completed visit | `src/components/AppointmentModal.tsx:180` sets `last_visit` to the appointment start date before a visit has occurred. It additionally derives that SQL DATE through UTC ISO slicing, which can move a late evening São Paulo appointment into the next date. Dashboard recency sorts on this field. CSV import similarly sets `last_visit:today` for every imported new patient (`src/lib/patientImport.ts:59`). | Separate registration date, next appointment, and last completed encounter. Allow no previous visit, derive completed recency from actual encounters, and preserve explicit imported dates only when known. Test a first appointment next month and a22:00 clinic appointment. |
| W7 | P2 | Google event creation lacks durable retry identity | `supabase/functions/sync-google-calendar/index.ts:149–165` POSTs a new provider event and only then stores its returned ID. A provider success followed by failed DB persistence leaves the local row unlinked; retry can create another event. Concurrent calls can both observe null. `src/components/AppointmentModal.tsx:223–242` runs sync without durable queue state; a toast is the only failure record. | Persist an outbox operation and stable provider creation identity, serialize/reconcile attempts, and expose pending/failed/synced state with retry. Prove that provider success plus DB failure and concurrent retries produce one event. The partial-success path is verified in source; no real Google mutation was performed. |

Related findings are owned by other review streams: draft-discard cleanup can orphan audio (security review); patient-directory editing omits revision CAS, calendar patient-query failures resemble an empty list, and reminders can include completed/past appointments (UI review). They should be deduplicated in the final roadmap rather than counted twice.

## Recommended functionality roadmap for the clinic pilot

Scope sizes are relative engineering scope, not duration promises: **S** = one focused slice; **M** = several coordinated UI/API/data changes; **L** = an epic requiring smaller slices. Priorities indicate sequencing/value for the stated clinic context, not confirmed buying intent.

| ID | Recommended slice | Value / priority | Scope | Dependencies | Acceptance / evidence |
|---|---|---|---|---|---|
| F01 | Verified patient identity | Pilot foundation | M | W1,W6 data-model correction | Nullable unknown age/date of birth with provenance; unambiguous name+DOB/record number in chart/recording/review/document surfaces; duplicate candidates require human resolution. Same-name patients remain distinguishable. |
| F02 | Appointment-linked encounter | Pilot foundation | M | F01,W2 | Opening a scheduled visit carries the appointmentID through the draft; one finalized encounter completes exactly that appointment; unscheduled encounters remain independent. Prove two same-day visits. |
| F03 | Private doctor workspaces and optional patient sharing | Required before enabling sharing | L | Explicit ownership/grant design; security review | Individual logins, private lists and author attribution; sharing grants name the doctor, patient, scope and permissions; revocation removes subsequent access; no clinic-wide visibility by default; cross-owner, stale-session, file, draft, document, export and model-context denial tests. Receiving a share does not transfer ownership or authorize deletion. Reception roles are deferred. |
| F04 | Work-in-progress consultation queue | Pilot productivity | M | Draft durability, F02 | Home lists recoverable/error/review drafts with patient, source encounter, age and last-save status; any draft opens on its original patient; retries are idempotent; a visible counter never equates draft with finalized record. |
| F05 | Manual typed encounter | Pilot resilience | M | F02; review/finalization contract | Start, edit, autosave and finalize a typed encounter without microphone or AI availability; no quota needed to save clinician-authored text; preserve the same provenance/revision and completion semantics as recording. |
| F06 | Direct draft editor and change review | Pilot productivity | M | W3, F04 | Edit generated text before first save; show AI-to-physician changes and transcript/source snippets; AI regeneration is optional and never overwrites edits silently; final save binds exact reviewed content. |
| F07 | Cited chart assistant | Pilot trust | M | W4 retrieval contract | Answers contain clickable source documents/visits and dates; visible searched coverage; older evidence retrieved when relevant; explicit “insufficient context” on gaps; no automatic patient treatment actions. Evaluate with synthetic known-answer and contradictory-source cases. |
| F08 | Urology and separated gyn/ob encounter templates | Pilot specialty fit | S initial templates; M versioned selection | Clinician-approved content; user settings/schema support | Add urology to supported specialty values (currently absent); offer separate gynecology, prenatal and urology visit templates; omit unmentioned facts; template version bound to each draft. Validate against clinician-approved synthetic examples before use. |
| F09 | Durable calendar sync status | Pilot operations | M | W7, F02 | Outbox pending/retry/synced/failed visible per appointment; retry produces one remote event; conflicts use explicit precedence; revoked authorization gives reconnect guidance. |
| F10 | Results and follow-up task inbox | High-value next phase | M | F02,F03 ownership | Clinician turns an exam/referral/return plan into a task with owner/due date; reassignment to another doctor requires appropriate patient access; receipt and clinical review are different states; nothing auto-closes solely because a file was uploaded. |
| F11 | Longitudinal medication reconciliation | High-value next phase | M | F01,F06 | Explicit active/changed/stopped medications with effective dates and provenance; physician reviews additions and removals; source conflict and dose change visible; generate documents only from an explicitly selected reconciled list. |
| F12 | Pregnancy episode workspace | Specialty differentiation | L | F01,F02,F06,F10 | Each pregnancy has its own clinician-confirmed dating data and provenance; maternal observations/results and planned appointments stay in the correct episode; corrections are versioned; clinically meaningful calculations require approved rules and tests. Do not infer a pregnancy or auto-change dating from free text. |
| F13 | Structured vitals and trend view | Specialty differentiation | M | F01,F02 | Store observation value/unit/time/source and corrected version; display trends without guessing absent values or silently converting units; validate out-of-range input without diagnosing; keep raw source accessible. |
| F14 | Versioned patient instructions and referrals | Next phase | M | F06; document storage contract | Physician can edit/approve, archive and reopen a patient summary/referral; sent content is a specific approved version; patient-facing wording does not imply secure delivery merely from opening WhatsApp. |
| F15 | Clinician-approved knowledge library | Next phase | M | F07; ingestion retry design | View original text and cited chunks; record source/version/review date; retry failed ingest without duplicates; update/retract superseded versions; assistant cites the actual approved version. |
| F16 | Signature provider and owner document archive | Gate if paperless signed issuance is required | L | Chosen provider; verified signature model; release/legal validation | Signed status only follows verified provider completion; retry and revoked/expired certificate cases tested; clinicians can inspect immutable historical documents while public validity remains correctly revoked/expired. Existing generated PDFs remain explicitly unsigned. |
| F17 | Reminder and confirmation workflow | Next phase | M | F02,F03,F09 | Provider outcome ledger distinct from queued/opened/delivered/confirmed; do not send for completed/canceled visits; channel preference and confirmation are explicit; failed contact uses a visible doctor-owned task. |
| F18 | PersonalMed2005 migration staging | Later, per user direction | L | Separate approved migration scope; exported-data inspection and mapping | Preserve original source IDs, original clinician identity and dates; map records into the correct doctor's private list; dry-run counts, duplicates and rejected rows; reconcile chart/document samples; produce a reversible import batch with no silent overwrite. Existing exports have not been read during this review. Optional patient sharing must not accidentally merge doctors' independently held records. |

For the initial rollout across doctors, F01–F08 are a better core than adding billing, autonomous clinical alerts, or a patient portal immediately. Every doctor can have a private workspace first; F03 must be complete before optional sharing is switched on. Sharing should remain disabled until its full data-access surface is covered. F12 creates stronger specialty value once identity, encounters, source review and task ownership are dependable.

## Suggested delivery order and success measures

1. **Release correctness:** resolve W1–W4 and the security/UI findings; add the corresponding regression tests. Complete outstanding staging checks from the prior remediation report. Do not reuse this report’s positive reproduction tests as fix assertions; invert them to the intended safe behavior when implementing.
2. **One clinic encounter end to end:** verified identity→scheduled encounter→recorded or typed draft→clinician review→finalization→one completed appointment→versioned patient instructions. Observe actual clinician tasks using designated test data first.
3. **Controlled sharing between doctors:** private lists, explicit per-patient grants, authorship, revocation, access audit and independently tested export/Storage/model-context behavior. Reception remains a later product scope.
4. **Specialty depth:** urology/gyn/ob template validation, structured observations, pregnancy episodes, source-cited longitudinal review.
5. **Integrations and scale:** signed issuance if required, the separately scoped PersonalMed2005 migration, larger exports and measured performance on clinic-sized datasets.

Measure task completion and failure recovery rather than only generated-note counts: time from encounter end to approved record, percentage of pending drafts recovered, completion of the correct linked appointment, patient-identification corrections, clinician editing burden, citation coverage for chart questions, overdue task review, and sync retry success. Establish a pilot baseline before setting numeric improvement targets. Collect operational metrics without raw transcript or patient content in telemetry.

## Confirmed rollout constraints

- Haddad Nicola is the first clinic; all doctors are in the intended initial rollout.
- Each doctor keeps a separate patient list; sharing is optional and explicit.
- Reception functionality is outside the initial scope.
- Existing records originate from PersonalMed2005; export files have already been downloaded, and migration is later work.
- An API/signature-provider choice and the exact clinical visit template content should be specified during implementation. This report proposes no unverified medical rule or automatic treatment decision.
